### Shipping

**You own what lands. Verify each PR independently, land only the verified run, then keep your hands off the queue.** For "land the stack", "ship it", "merge these", or the second half of a set of PRs that **Babysit** already drove to green.

This is the half after `playbooks/babysit.md`. Babysit makes PRs mergeable. Shipping decides what is actually safe to merge and lands it. Green is not safe, and the gap between those two words is where this playbook lives.

1. **Verify every PR independently before merging anything.** One subagent per PR, not batched, each in its own worktree, each exercising the real surface (the `verify` skill for UIs, `run` for CLIs and TUIs, as the change demands) against parent versus head. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR so the record outlives the chat. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** For a chain of dependent branch-on-branch PRs, walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain. Independent PRs off trunk have no chain; each merges on its own verdict.
3. **Re-check that the verdicts still describe the code.** A rebase rewrites every SHA above it and silently invalidates every verdict without touching a single check. Compare `git patch-id` at the verdict SHA against the current head before trusting an older verdict, and re-verify anything that actually drifted. Twenty-one verdicts went stale this way in one run with no signal at all.
4. **Merge in dependency order with `gh`.** For each PR in the verified run, bottom-up: merge it (`gh pr merge <n> --squash`, or the repo's convention), then retarget the next PR in the chain onto the new trunk (`gh pr edit <n+1> --base main`, then `git rebase --onto main <parent-branch>` on its branch, push with `--force-with-lease`), and confirm the retarget took before merging it. The `--onto` form is load-bearing: after a squash merge, the child branch still carries the parent's original commits, and a plain `git rebase main` replays them into conflicts. Keep the merged parent's branch until its child is rebased — it anchors the `--onto`, and deleting it fires GitHub's automatic base retarget, which races the manual one. Read back each merge with `gh pr view <n> --json state,mergedAt` rather than assuming the command's exit code told the whole story.
5. **Arm auto-merge only on PRs that target protected trunk.** `gh pr merge --auto` on a PR whose base is another PR's branch merges the child into its parent the moment checks pass and collapses the chain into itself. Auto-merge is for the bottom PR only, after its verdict; every child waits for its own retarget-and-verify pass. If a previous agent armed auto-merge on a child, disarm with `gh pr merge <n> --disable-auto` and confirm the field is back off.
6. **Once merges are in flight, stop touching the branches.** No speculative rebases, no pushes to branches above the merge point, no cleanup commits. A push to a mid-merge chain retargets bases underneath you. Independent work gets re-based onto trunk and shipped on its own.
7. **Watch the drain, do not drive it.** Poll with the watcher (`skills/poteto-mode/scripts/watch-pr/watch-pr` under the installed plugin) in queued mode over the verified run and hold it under `/loop` in dynamic mode, re-armed after any verdict you act on, until COMPLETE at the ceiling. ADVANCE is progress, not termination. Report each merge and the new ceiling. If a merge stalls, diagnose before mutating, because a stalled queue and a broken chain look identical from the outside.
8. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Trunk and promotion.** `main` above means the repo's integration trunk — the branch PRs merge into. In a staging-first repo (PRs land on a `staging` branch that auto-deploys a staging environment, and a separate promotion PR carries staging into the production branch), this playbook's job ends when the verified run has landed on the integration trunk and the staging deploy is verified live against the real environment. Promotion to production is a separate operator-gated pass under the repo's own runbook — prerequisites like DB migrations and infra deployments are the operator's, the promotion PR merges only on the operator's click, and it is never an extension of this playbook's merge loop.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you merged and how you confirmed it, and what the next gap needs.
